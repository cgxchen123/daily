# 用分支保护减少直接推送到 main 的风险

主分支通常代表团队认可的集成状态。如果每个人都可以直接推送，未经审查的代码、遗漏的测试和误删文件就可能立即影响其他人。分支保护把部分约束放到仓库平台，而不是只依赖团队口头约定。

## 建议的保护条件

- 要求通过 Pull Request 合并。
- 对关键目录要求至少一名审查者批准。
- 要求指定的 CI 检查成功。
- 阻止强制推送和分支删除。
- 对发布分支设置更严格的权限。

具体设置名称会随 GitHub 版本和仓库计划变化，应以仓库当前设置页面及官方文档为准，不要假设每个仓库都能启用所有选项。

## 本地合并前先检查

```bash
git status --short
git diff --check
git diff --staged
```

这些命令帮助发现工作区状态、部分空白错误和暂存差异，但不能代替代码审查或自动化测试。

## 保护规则也要维护

分支保护并不是一次设置后就不用管。检查规则是否要求正确的 CI 工作流，确认紧急修复流程有审计记录，并定期移除已离职人员的权限。管理员绕过规则的能力也应被明确限制和记录。

## 常见失败模式

如果 CI 检查名称被修改，保护规则可能一直等待不存在的检查；如果测试没有覆盖关键行为，即使全部通过也不能证明系统正确。审查者也应重点查看权限变更、依赖升级和配置文件。

分支保护的价值在于把团队约定变成可执行的合并门槛，同时保留必要的紧急处理和审计路径。
