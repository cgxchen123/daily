# 避免异常泄露内部细节

将堆栈、SQL、内部路径或供应商响应直接返回客户端，可能暴露系统结构。客户端应获得稳定错误码和可操作的简短说明；完整诊断信息应放在访问受控的日志中，并确保日志本身不含秘密。

## 推荐做法

先将目标写成可检查的条件，明确输入来源、失败方式和可恢复状态。把核心规则与外部 I/O 分开，避免同一段代码同时负责校验、执行、记录和补偿。涉及第三方服务时，应记录版本、时间和调用上下文，但不要记录密码、令牌或完整敏感数据。

## 防护与验证

至少测试正常请求、边界值、恶意格式、权限不足和超时。检查拒绝路径没有留下半成品或副作用；对外错误应稳定且不泄露内部实现。

```python
def public_error(error_code: str) -> dict:
    allowed = {"INVALID_INPUT", "NOT_FOUND", "UNAVAILABLE"}
    if error_code not in allowed:
        error_code = "UNAVAILABLE"
    return {"error": error_code, "message": "Request could not be completed"}

if __name__ == "__main__":
    assert "traceback" not in str(public_error("NOT_FOUND"))
    print(public_error("NOT_FOUND"))
```

## 验收清单

- 明确正常结果与失败结果。
- 至少覆盖一个边界或异常案例。
- 记录实际验证环境和未覆盖限制。
- 不把示例代码或静态检查宣称为生产验证。
