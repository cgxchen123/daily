# 用 git log 定位回归

回归定位需要先明确问题首次出现的范围，再结合提交历史和可复现测试缩小范围。git log 能提供变更线索，但提交说明并不能证明实际影响；应比较差异并在可控环境中复现故障。

## 推荐做法

先将目标写成可检查的条件，明确输入来源、失败方式和可恢复状态。把核心规则与外部 I/O 分开，避免同一段代码同时负责校验、执行、记录和补偿。涉及第三方服务时，应记录版本、时间和调用上下文，但不要记录密码、令牌或完整敏感数据。

## 可执行检查

```bash
git status --short
git log --oneline -10
git show --stat <commit-sha>
git diff <known-good-sha>..<suspect-sha>
```

在真实仓库执行前，先确认当前分支和工作区状态。示例中的占位提交 SHA 需要替换成实际值；不要在未审查差异时执行破坏性操作。

## 验收清单

- 明确正常结果与失败结果。
- 至少覆盖一个边界或异常案例。
- 记录实际验证环境和未覆盖限制。
- 不把示例代码或静态检查宣称为生产验证。
