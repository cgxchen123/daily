# 处理合并冲突前先保存现场

出现合并冲突时，应先查看 git status 和冲突文件，再逐块理解双方修改的意图。不要只选择 ours 或 theirs 就提交；冲突解决后必须检查最终差异并运行相关测试。若工作区还有无关修改，应先备份或隔离，避免把它们一起带入合并。

## 实施建议

先定义要保护的状态、输入边界和失败时的行为。把验证与副作用分开，明确并发执行、重试和回滚的约束。涉及第三方组件时，记录具体版本、权限和运行条件，避免仅凭默认行为推断安全性或正确性。

## 示例

```bash
git status --short
git diff --name-only --diff-filter=U
# 编辑并解决冲突后：
git diff --check
git diff --staged
```

## 验收清单

覆盖正常输入、边界输入和失败路径；检查日志不含秘密，重复执行不会产生非预期副作用。示例仅展示核心机制，生产环境仍需结合实际框架、权限和并发模型验证。未实际运行的检查不得宣称通过。
